# crb HTTP API contract (v1)

Base path `/api/v1`. JSON everywhere. This document is the contract the server
(`crb.server`) implements and the UI (`ui/`) consumes; both are built against it
in parallel, so changes here are changes to both.

> **Driving the API from an assistant:** every route below that a model should reach is also a
> Model Context Protocol tool — see [MCP](MCP.md) (`crb mcp`); the tools relay these responses
> unchanged.

## Conventions

- **Auth**: cookie session (`crb_session`, HttpOnly, SameSite=Lax, Secure in prod).
  Login via `POST /auth/login` (local account) or `GET /auth/oidc/start` → provider →
  `GET /auth/oidc/callback` (Entra ID / any OIDC). `GET /auth/me` returns the principal.
  Mutating requests must carry `X-CSRF-Token` equal to the `crb_csrf` cookie.
- **Roles** (ascending): `viewer` (read everything), `operator` (+ create/cancel runs,
  add/probe repos, mine), `approver` (+ sign-offs), `admin` (+ users, settings).
  A route lists its minimum role. 401 = not logged in (`unauthenticated`, `session_expired`,
  `session_revoked` — the account's password changed after the cookie was issued, which is
  what ends a session for good, or `unauthenticated` with "account unknown or disabled" —
  the account is deactivated: every request is refused while it is inactive, but the session
  is not revoked, so requests resume with the same cookie once an admin re-activates the
  account within the session lifetime, `CRB_SESSION_TTL`; see OPERATOR.md §9 and
  SECURITY.md), 403 = insufficient role.
- **Errors**: `{"error": {"code": "<snake_case>", "message": "...", "detail": {...}}}`.
  `409 false_q1_refused` is reserved for sign-off refusals and ledger invariant
  violations; `503 sandbox_unavailable` for fail-closed sandbox stops;
  `422 builder_credential_missing` for a run refused at submit because a builder it would
  call has no credential for its auth.
- **Pagination**: `?limit=` (default 50, max 500) `&offset=`; responses carry
  `{"items": [...], "total": n, "limit": l, "offset": o}`.
- **Numbers carry their method**: every rate is accompanied by `n`, `ci_low`, `ci_high`
  (Wilson 95%), `apparatus_versions`, and `belt_set` where mixed.
- **Never fabricated**: an unmeasured cell is `NOT_YET_MEASURED`, never an empty row.

## Health / metrics (no auth; bind to an internal interface)

| Method | Path | Returns |
|---|---|---|
| GET | `/health` | `{"status": "ok|degraded|down", "probes": [{name, status, detail, data}], version, apparatus, role, checked_at}` — ten probes: `db`, `migrations` (the store's Alembic revision is the code's head — the contract is [The `migrations` probe](#the-migrations-probe) below), `append_only` (the ledger triggers exist AND an UPDATE is refused), `ledger` (row count and `false_q1`, `down` on any false-Q1 row), `sandbox` (`skipped` for `CRB_ROLE=api`), `toolchains`, `builders` (credential presence), `worker`, `intake`, and `build` — the served commits agree: the commit the process was started from (`CRB_SOURCE_COMMIT` in an image, else the checkout's HEAD at start-up), the checkout's commit now, and the commit the served UI bundle was built from (its `build-stamp.json`); any disagreement, or a served bundle with no stamp, is `degraded` (never 503 — stale code still serves) with the fix in the detail, and `skipped` when no commit can be named. The body's top-level `served` = `{server_commit, checkout_commit, ui_commit, ui_stamp: stamped|unstamped|unreadable|absent, stale, reasons[]}` (`{}` when the read failed); no path is ever served (docs/PREVENTION.md P-002). The `worker` probe reads the `workers` table each worker upserts every `heartbeat_s` even when idle: `data.workers[]` = `{worker_id, hostname, executor, kinds, started, heartbeat, heartbeat_age_s, stale_after_s (3 × the worker's own heartbeat_s), current_run_id, version, stopped, alive, unconfirmed_containers}` plus `alive` (workers alive now), `running` (running runs), `queued` (queued runs), `stale` (ids of running runs whose heartbeat is older than the top-level `stale_after_s`), `stale_after_s` (the RUN staleness threshold, the `worker_heartbeat_stale_s` setting — a run's heartbeat, not a worker's: each worker's own `stale_after_s` is `3 × its heartbeat_s` and decides `alive`) and `unconfirmed_containers` (the sum over the listed workers of containers whose `docker kill` the daemon never confirmed and the worker's reaper is still retrying — `POST /runs/{id}/cancel`); `degraded` — never `down`: `/health` is the API pod's readiness probe and the worker is a dependency the API does not own — when runs are queued and no worker is alive ("2 runs queued, no worker has checked in for 360 s (w-1) — queued runs will not start until a worker does"; behind a clean stop "1 run queued, the last worker (w-1) stopped 40 s ago …"), when no worker has checked in yet, when one stopped checking in (named, with its age), when a running run's heartbeat is stale, or when `unconfirmed_containers` > 0 ("2 containers whose docker kill was not confirmed are being reaped by worker w-1 — each may still be running on its host; `docker ps` there names them and `docker rm -f <name>` reaps one by hand"); `ok` = "1 worker, last check-in 4 s ago · 2 runs queued". 503 on `down`. **A probe whose read raises never serves the exception**: it is `down` with the one fixed detail `<probe> could not be read — see the API log, request id <id>` and `data: {}`; the exception is logged under that id (the `X-Request-ID` the response echoes) — the route is unauthenticated (CWE-209) |
| GET | `/health/live` | – | process up + database reachable; never probes the sandbox (container HEALTHCHECK / Helm liveness); 503 when the store is gone |
| GET | `/metrics` | Prometheus text — the **API process's** series only: `crb_http_*`, `crb_ledger_rows` and `crb_false_q1_total` (recounted on every scrape; must be 0). Every build / grade / cost / delivery series is recorded in the **worker** process and served on the worker's own port (`CRB_METRICS_PORT`, default 9464) — see [DEPLOYMENT.md §9](DEPLOYMENT.md#9-observability) for the table of which process carries which series. 404 `metrics_disabled` when `CRB_METRICS_ENABLED=false`; 503 `metrics_unavailable` without `prometheus_client` |
| GET | `/version` | `{"crb": "...", "apparatus": "2.2", "policy": "routing.v1", "uptime_s": 0, "oidc_enabled": false}` — `oidc_enabled` says whether an organisation (OpenID Connect) sign-in is configured, so the login page offers the button only when it works and the posture page can state the sign-in mode; it names no provider and no secret |

### The `migrations` probe

The one statement of the contract. [DEPLOYMENT §8](DEPLOYMENT.md#8-go-live-checklist),
[OPERATOR §1.1](OPERATOR.md#11-check-the-installation-crb-doctor) and the CHANGELOG repeat
its sentence and link here; `crb doctor`'s `migrations` line renders the same
`migrations_result`, so the two surfaces cannot disagree. In one sentence: `ok` at head; `degraded` (still served) for an unstamped `create_all` schema that matches the head, until `crb migrate` stamps it; `down` (the endpoint answers 503) when the store is behind, ahead, empty or an older unversioned schema (crb tables, no `alembic_version`, fingerprints of a revision behind the head) — revisions named where applicable, with the fix — or when it cannot be read — the fixed detail `migrations could not be read — see the API log, request id <id>`, `data: {}`, the exception in the API log under that id.

| State | HTTP | `detail` | `data` |
|---|---|---|---|
| `ok` — at head | 200 | `database at <rev> = code head` | `{database, head, at_head, unversioned_at, matches_models}` |
| `degraded` — an unstamped `create_all` schema that matches the head (complete; still served) | 200 | ``schema matches head <rev> but carries no alembic_version (a create_all store) — run `crb migrate` to stamp it`` | the same shape |
| `down` — behind or ahead | 503 | ``database at <db rev>, code head <rev> — run `crb migrate` …`` | the same shape |
| `down` — empty, or an unversioned older schema | 503 | ``database not migrated (empty)`` or ``database not migrated (unversioned schema at <rev>)``, then ``, code head <rev> — run `crb migrate` …`` | the same shape |
| `down` — cannot be read | 503 | `migrations could not be read — see the API log, request id <id>` (fixed; the exception is in the API log under that id, never served) | `{}` |

## GitHub App (the enterprise connection — ADR-0014, docs/GITHUB-APP.md)

| Method | Path | Role | Notes |
|---|---|---|---|
| GET | `/github/app` | viewer | `{configured, app_slug, install_url, api_url, installations: [{id, account_login, account_type, repository_selection, html_url, suspended, permissions, can_deliver, recorded_by, updated}]}` — never 404s; `configured: false` is a state. For an operator or above, `install_url` carries `?state=` — a signed, thirty-minute value bound to the operator and to a nonce the same response sets as the httponly cookie `crb_github_setup`; GitHub passes the state back to the setup callback, which needs both; a viewer's link is plain |
| GET | `/github/setup?installation_id=&setup_action=&state=` | operator | the app's **Setup URL**: verifies the installation with the app credential (`GET /app/installations/{id}`); when `state` is one this deployment signed for this operator and its nonce matches the `crb_github_setup` cookie (see `GET /github/app`), records it and expires the cookie (one state, one write) (+ `github.installation.recorded` event) and 303 → `/connect?installation={id}`; otherwise writes nothing and 303 → `/connect?installation={id}&unverified=1`, where the operator records it with `POST /github/installations/sync` (CSRF-protected, same verification) — request-intent protection for a GET that writes (CWE-352) |
| POST | `/github/installations/sync` | operator | refresh from GitHub; an installation GitHub no longer lists is marked `suspended` |
| GET | `/github/installations/{id}/repositories?q=&page=&per_page=` | viewer | the picker: `{items: [{full_name, name, html_url, clone_url, default_branch, private, language, archived, suggested: {name, language, runner}, connected_as}], total, page, per_page, has_more}`. `q` filters the requested GitHub page only (GitHub's installation listing has no search); `total` and `has_more` describe the unfiltered listing, so a match can sit on a later page — the UI says so and offers *Next* |
| POST | `/github/installations/{id}/connect` | operator | `{full_name, name?, language?, runner?, src_prefix?, test_prefix?, ext?, test_mode?, test_suffix?, belt_scope?}` → 201 `RepoDetail` whose `config.url` is the clone URL and whose row carries `config_json.github = {installation_id, full_name, default_branch, html_url, private}`; 404 when the installation cannot see it, 409 `already_exists` (with `detail.repo`; the same GitHub repository connects once — `repos.github_full_name` is unique in the database, so two simultaneous connects cannot both succeed), 422 when GitHub reports no language and none is given (`detail.suggested`); the same `full_name` grammar and answered-with-the-repository-asked-for guards as `POST /repos/{name}/github-link` (422 / 502). `PUT /repos/{name}` with a different `url` drops the GitHub link (`github_unlinked: true` on the `repo.updated` event): a token is only ever sent to the host the link was made for |
| POST | `/repos/{name}/github-link` | operator | `{installation_id, full_name}` → 200 `RepoDetail`: link an **existing** repository to one of the installation's repositories. The row keeps its name (and so every ledger row, map and sign-off made under it); `url` becomes the https clone URL, `github_full_name` the lower-cased `owner/name`, `config_json.github` the same link dict connect writes; language, runner, layout and belt scope are not touched (edit them with `PUT /repos/{name}` if the fork differs) and an existing clone is kept. Re-linking the row to another repository replaces the link. Recorded as a `system/repo.github_linked` event on the repo's trace with `{github, url_before, url_after, previous_full_name, fields: ["url"], diff: {url: {from, to}}}` (`previous_full_name` `null` on a first link; `fields` / `diff` are the `repo.updated` shape, so the audit trail renders the change). 404 unknown repo / installation not on record / repository not visible to the installation; 422 archived, or a `full_name` that is not GitHub's grammar (a login of alphanumerics and hyphens; a name of `[A-Za-z0-9_.-]`, never a dot segment), or a repository GitHub now answers under a **different** name (renamed / transferred — `detail.full_name` names it: select it under its current name); 502 `github_error` for GitHub's 301 (a renamed repository the API answers with a redirect, which the client never follows — `detail.github_status: 301`) or an answer that is not a repository (no `full_name` / `clone_url`) — the row is written only when GitHub's answer IS the repository asked for; 409 `already_exists` (`detail.repo`) when that GitHub repository is linked to a **different** row (the same unique index decides a race); 403 viewer. The honesty note: the ledger rows keep their repo name, the events row is the seam an auditor reads, and a fork of the same history (`cobra` measured on `spf13/cobra`, delivered on `Jita81/cobra`) is the case this exists for — a link to a repository with a different history keeps the old evidence under the name too, which is why the event carries both URLs |

Errors from GitHub are 502 `github_error` with `detail.github_status`; an unconfigured app is 404 `github_app_not_configured` on every route but `GET /github/app`. No response, row, event or log ever carries an installation token.

## Runs

| Method | Path | Role | Notes |
|---|---|---|---|
| GET | `/runs` | viewer | page, newest first; filters `repo`, `kind`, `status` |
| POST | `/runs` | operator | `{repo, kind: setup|probe|mine|replay|blind|oracle|controls|label|factory, mode?, builder?, model?, provider?, ladder?, budget?, task_ids?, limit?, pool?, executor?, timeout?, builder_config?, retain?, outage_stop?, preflight?, budget_profile?, escalation?, checks?, learning?}` → 201 run (status `queued`). `learning: "off"` opts THIS run out of the repository's prevention loop (ADR-0020): no playbook line and no overlay reach its builder and every row reads `learn: off`; a run may opt out, never in; stored as `params.learning` only when set. `ladder` is a list of at most 16 entries, one attempt per rung until an attempt grades clean, default `["r1"]`; each entry is a rung LABEL (`r1`, `r2` … = one attempt with the run's own `builder:model[@provider]`; `builder:model[:provider]` = a rung as written) or an OBJECT rung `{builder, model, provider?, budget?}` whose `budget` overrides the run's for that rung only — so `[{builder, model, budget: {max_tool_calls: 25}}, {…50}, {…100}]` is a **budget ladder**: the same model, escalating caps, climbed until clean. A rung accepts nothing else (`name`/`config`/a builder kwarg/a credential-shaped key → 422 with the rung's own reason); exact-duplicate rungs and repeated labels are 422; a ladder made only of object rungs needs no run-level `builder` (the first rung fills the run's builder/model/provider). `ladder_json` stores the ladder exactly as declared and `GET /runs/{id}.ladder` echoes it. `budget` is the run-level per-attempt cap set `{max_turns?, max_tool_calls?, max_tokens?, max_cost_usd?, wall_clock_s?}` — every field optional, bounded (`1 ≤ max_turns ≤ 1000`, `1 ≤ max_tool_calls ≤ 5000`, `0 ≤ max_tokens ≤ 50 000 000`, `0 ≤ max_cost_usd ≤ 1000`, `1 ≤ wall_clock_s ≤ 86400`; `0` tokens / `$0` = no cap), stored as `params.budget` with ONLY the fields set (`{}` → not stored) and applied by the worker as **rung > run > builder default, per field** (defaults `25 turns / 25 tool calls / 0 / 0 / 900 s`); the effective budget of every rung is validated before any task runs (a bad cap fails the run closed). `kind: blind` implies `mode: blind`; `replay`/`blind` need a `builder`. `outage_stop` (default 3, `0` disables) is the **provider circuit breaker**: after that many consecutive attempts the provider refused (`failure_kind: outage` — usage limit, 429, dead credential) the run stops `failed` with `provider outage: N consecutive attempts refused; last: …` and a `system/run.outage_stop` event, instead of writing a refused row per remaining attempt. `preflight` (`true` or `{fix: bool, repair_turns: 0–3}`) switches on the **belt-5 pre-flight** for a build run: after an honest build the repository's own linter/formatter plan runs on the changed files; if it rejects, the plan's tools run in fix mode (`prettier --write`, `ruff check --fix` + `ruff format`, `eslint`/`standard --fix`, `gofmt -w`, `cargo fmt`) and then, if still rejected, the builder gets ONE bounded repair call with the findings. The run's rows carry the builder as `<name>+preflight` (a different arm — its cells never pool with plain rows), `labels.preflight` records what happened (`fix=1,repair=1;before=rejected;fix=prettier:0;after_fix=clean`), both calls are one attempt's spend, and the apparatus stamp carries `extra.preflight`. `checks` (`{format_step?, finish_gate?, api_stable?}`, each `true`/`false`/absent) overrides the repository's `checks` switches for this run (run > repository > OFF; stored as `params.checks` with only the fields set): `format_step` runs the repository's OWN formatter (the belt-5 plan's `gofmt`/`ruff format`/`prettier`/`cargo fmt`, black when configured, or the declared `checks.formatter`) over the changed non-test files after the build and before the grade — skipped with a named reason when none is configured; `finish_gate` puts the repository's checks in the brief as a numbered checklist, re-runs them after the build and gives the builder up to `finish_repair_turns` bounded repair calls, and `done` is accepted only when they pass (a declared command already red at the parent is `pre_existing` and does not gate; a blind checklist that would name the held-out oracle is refused before any spend); `api_stable` evaluates **belt 6** in the grader (the public API of the changed units is unchanged unless the gold changes it the same way; failure kind `api`). Every row of a run with any switch on, or of a repository with a non-default block, carries `labels.checks` (`fmt=1:repo;gate=0:default;api=1:run;cfg=<12-hex config version>`) and, when a step ran, `labels.format_step` (`ran=gofmt;changed=1` / `skipped=no_formatter_configured`), `labels.finish_gate` (`before=fail:lint;repair=1;after=pass`) and `labels.api_stable` (`true`/`false`/`none`) with `labels.api_findings` (`kind:unit:symbol;…`); the evidence pack's notes carry the format step's changed files and the gate's per-check results; the apparatus stamp carries `extra.checks`. **Spend switches** (build kinds; `crb.core.spend`): `budget_profile` — `default` (as declared) or `calibrated`: each attempt runs under caps taken from the ledger's own clean completions in its cell (same builder and model, valid rows, `repo × mode × size` then `mode × size`, at least 8 clean rows; each cap = p90 × 1.5 of what they used — wall clock from `latency_s`, turns from the packs' `builder.turns`, tool calls scaled with turns — never below the run's caps and never above twice them); it changes what the builder is given, so it is OFF unless asked, and every row records `labels.budget_profile`, `labels.budget_calibration` (the level, n and p90s, or `floor:<why>`) and `labels.budget_tier` of the caps it actually ran under. `escalation` — `measured` (the default) or `always`: before a non-clean, non-disqualified attempt climbs to the next rung, the worker reads that rung's prior escalated attempts (trial `r2`+, same builder and model, valid rows; `repo × mode × size`, then `mode × size`, then `mode`, at least 10) and withholds the climb when their clean yield is under 10%; the row that stopped or climbed carries `labels.escalation` (`stopped` / `climbed`) and `labels.escalation_rule` (e.g. `measured:mode=blind:yield=2/40<0.10`, or `measured:insufficient:n=4<10:bar=0.10`), and a `run.escalation_stopped` event names the task. Absent = the repository's `config.spend` (`PUT /repos/{name}`), else the default; the run's apparatus carries `extra.spend {budget_profile, escalation, sources, observations, escalation_rule, calibration_rule}`. Both read only the rows that existed when the run started. `kind: mine` with `task_ids` **re-qualifies** exactly those commits (known or not — for after the miner changed): each is walked under the pool it was stored under (the pool's shape caps apply; an unknown id takes the run's `pool`), the stored spec is replaced, grade rows are untouched, and a sha that no longer qualifies is left as it was with a `mine.skip` event saying why. A build kind without `model` gets the builder's default when it has one (`claude_code` → `CRB_CLAUDE_CODE_MODEL` on the API host, else `claude-sonnet-5`; the stored run names it). `builder_config` is an object of builder constructor keyword arguments applied to every rung (e.g. `{"auth": "cli", "effort": "high"}` for `claude_code`) — stored as `params.builder_config`, passed to the worker as builder overrides and stamped into the run's apparatus (`extra.builder_config`); keys must be lowercase identifiers, at most 32 keys / 8 KiB; `model`, `provider`, `name` (the recorded identity) and credential-shaped keys (`*api_key*`, `*token*`, `*secret*`, `*password*` …) are 422. **A build run whose builder auth has no credential is refused at submit**: 422 `builder_credential_missing` with the fix in the message and `detail: {builder, auth}` — for `claude_code`, auth `api_key` (the default, or `CRB_CLAUDE_CODE_AUTH`) needs `ANTHROPIC_API_KEY` set, and auth `cli` needs `CLAUDE_CODE_OAUTH_TOKEN`, a stored token (`PUT /settings/secrets/claude-code-token`) or a `claude` CLI on PATH; every builder on the ladder is checked, nothing is queued, and it is a PRESENCE check only — no secret is read, returned or logged (the API checks its own environment; the shipped compose and Helm give the API and the worker the same one; docs/PREVENTION.md P-003). 404 unknown repo, 422 on any invalid field, 503 `queue_unavailable` |
| GET | `/runs/{id}` | viewer | `{id, repo, kind, status, mode, builder, model, provider, ladder, budget, executor, timeout, pool, limit, task_ids, builder_config, retain, actor, created, started, finished, cancel_requested, error, cost_usd, apparatus_version, apparatus, worker_id, heartbeat, counts: {tasks, clean, disqualified, errors, first_pass_clean, rows, duration_s, stopped_reason, detail}, progress: {done, total, current_task_id}, queue_position, queue_kinds_ahead, factory}`; `ladder` is `ladder_json` as declared (labels and/or object rungs — an object rung echoes only the budget fields it set); `budget` is `params.budget` (`{}` when the defaults apply); a replay's `apparatus.extra` carries `budget` (the run-level caps in full), `builder_config` and `ladder` (one `{builder, model, provider, budget_tier}` per rung, in order); ## Reviews (human verdicts on graded rows)

A review is a person's post-hoc verdict on ONE graded row (`crb.core.review.ReviewRecord`), kept forever as governance evidence (`docs/DATA-RETENTION.md`). The `reviews` table is append-only and hash-chained on its own (`prev_hash` = the previous review's `row_hash`; `row_hash` over the canonical record). **The patch-hash anchor:** a review with a verdict carries `patch_sha256_reviewed`, the SHA-256 of the unified diff the reviewer loaded through `GET /grades/{row_hash}/patch`, and the write boundary refuses it unless that hash equals the row's evidence pack `grade.diff.diff_sha256` — a reviewer attests to the exact bytes the instrument graded, never to a description of them. The verdict is DERIVED from the findings by one rule (`derive_verdict`: the most severe finding kind in `regression > defect > api_change > style`, `ok` with none); `not_reviewed` is the reviewer's explicit "I looked and could not review" (no findings, no `mergeable`, no hash).

## Factory (forward mode, P6)

The factory manufactures NEW work under the same governance as a replay: a frozen, hashed backlog → the DoR readiness gate (structural gaps only; value slots can never be signed) → a RED proof of the item's oracle → the build ladder under the belts (a `process_step=factory` ledger row + evidence pack per attempt) → opt-in delivery as a branch + PR (never the default branch) → an independent review whose verdict is recorded before any edit. State lives under `CRB_HOME/factory/<repo>/` (`backlog.json` + history, `evidence.jsonl`, `gaps.jsonl`, `authored.json`) — append-only and hash-chained like the ledger. **Running the loop is a run kind:** `POST /runs {repo, kind: "factory", ladder/builder…, deliver?: false, deliver_override?: false, max_rework?: 1, test_author?, backlog_hash?}` — **delivery is route-gated** (ADR-0003 amendments 2026-09-16 and 2026-09-19): with `deliver: true` a clean build gets a branch + PR only when its (class × size) cell routes `deliver` on the repo's signed capability map (sighted rows, current apparatus, the latest controls verdict) — read **once per item at readiness, before any build, from rows that precede this run** (the run's own rows are excluded, DL-045) and recorded on the item's `route.decided` event as `cell_route {route, reason, reason_code, n, point, ci_low, false_q1, policy_version, apparatus_versions}` (`null` = unmeasured), which is the reading the PR body quotes; any other route, or an unmeasured cell, withholds delivery as a `delivery.refused` event carrying `measured_route`, `reason_code` and `policy_version`, and the item is still reviewed. A rework after `accept_with_edit` **updates the pull request the first delivery opened** — a `delivery.updated` event (the `delivery.opened` payload plus `previous_commit_sha`, `updated: true`, `rework`, `after_verdict`, `comment_error`; the push leases against the previous commit, no second PR, a comment on the PR names the rework — when that comment fails after the push has moved the branch, `comment_error` carries the redacted failure, `body_sha256` is empty and the item is still reviewed, never `delivery_failed`) — and the task view's `pr_url` folds from whichever delivery event is newest on the chain. **A `weak_oracle` verdict never triggers a rebuild against an unchanged oracle** (DL-045 rule 3, B-1b finding 3): when the `accept_with_edit` verdict's findings carry `kind: weak_oracle` (the reviewer asks for a stronger TEST), the loop rebuilds only against an oracle whose sha256 differs — with no test author, or when the author returns the same bytes (or `null`), the item stops `oracle_needs_strengthening`: a `route.decided` event routes it `human` (reason: the finding and the way forward — *strengthen the test and register a superseding item*; `after_verdict`, `finding: weak_oracle`, `oracle_sha256`), the trace carries `rework.refused`, no edit is permitted for the no-author case, no second RED proof, build or push happens, and the pull request keeps the one reviewed build. A rework asked for any other reason keeps the ordinary path. **The test author** (G-904): an item with no operator-authored oracle stops `no_oracle` unless the deployment configures a test-author rung (`CRB_FACTORY__TEST_AUTHOR`, `builder:model[:provider]`) or the run names one (`test_author`, which wins; `none` in either place means no author). That rung writes one failing test for the item, in the repository's own test conventions, and it is trusted by nothing: the RED proof runs it at the base and requires RED with attributable failing ids, the oracle is staged as a throwaway commit and belt 1 re-checks every test byte. **The author rung and the build rung are never the same rung** — the same refusal that stops a rung building against its own test (`assert_distinct_identity`) is applied to every rung of the run's ladder when the run's spec is built, so a run configured that way fails before anything is built, not half-way through. The run's apparatus stamp carries `test_author` (`""` = none) and the trace carries `factory/author.configured`; each authoring attempt is `author.attempt` with the reason a reply could not be used. `deliver_override: true` is an **approver's** one-run override (403 below approver): the caller's identity is stamped into `params.deliver_override_by` and the override is a `route.decided` event naming the route it overrode. These fields are 422 on any other kind. The API stamps the ACTIVE backlog's hash into `params.backlog_hash` and its evolutions chain into `params.evolutions_hash` at enqueue (**409 `no_frozen_backlog`** when none is registered; a `backlog_hash` in the request must equal it — **409 `backlog_hash_mismatch`** with `detail.active`), the worker re-verifies both pins on claim (the run fails closed if the backlog was re-registered OR an evolution was registered in between — an evolution moves only the chain, never the frozen hash), walks the items in dependency order (the LATEST evolution of each item — `Backlog.ordered()`; a superseded item is never worked), and stops on cancel; `GET /runs/{id}` shows `counts.detail {items, done, accepted, by_status, outcomes[]}` and the apparatus stamp carries `backlog_hash` and `base_sha`. **Before the first item** (F39): on a repository with a URL the worker fetches it and fast-forwards the clone's default branch to the remote's (`system/repo.fetch.start` / `repo.fetch.done {before, after, fast_forwarded}`; a replay / blind / mine run does the same on a repository linked through the GitHub App) — a fetch that fails, or a local default branch that cannot fast-forward, ends the run `failed` with the reason (`FetchRefused: …`) before any RED proof or build, so nothing is ever built on a base the remote has moved past. **Then the outcome sync** (B-9 / F30): on a linked repository the installation token reads every delivered pull request's state and records `delivery.merged` / `delivery.closed` (at most closed then merged per PR) (`factory/outcomes.synced`; skipped with its reason on an unlinked repository; a token that cannot be minted is an error event, never a failed run).

## Learn — the prevention loop (ADR-0020)

A bug class is closed by a change the attempts prove. The register is computed on read from
the ledger, the review store, the factory's outcome events and the loop's own hash-chained
record; every write is one `learn.prevention.recorded` event on the repository's `learn:<repo>`
trace, made by the signed-in operator (never a field of the body). A chain that does not
verify is `409 prevention_chain_broken`, and nothing is written onto it. The guide is
[LEARNING-LOOP §7](LEARNING-LOOP.md#7-prevention--a-bug-is-closed-by-a-change-that-stops-it-recurring).

## Contract notes (server ↔ UI)

`ui/src/api/types.ts` is the UI's reading of this document; where the two differed the
UI's shape was adopted (2026-09-13, W2-B):

- `/repos` items carry `probe`, `task_counts` and `last_run` objects (not flat columns).
- `/runs/{id}` carries `counts` (`RunSummary.to_dict()` fields) and `progress` with
  `current_task_id`; `started`/`finished`/`heartbeat` are `null` when unset.
- `/runs/{id}/tasks` rows carry `belts` as an object and `pack_hashes` / `row_ids` lists.
- `/evidence/{hash}` is `{pack, verified, …}` (the pack is not inlined next to `verified`).
- `/capability-map` `summary.trusted_autonomy_coverage` is a number OR `null` (no profile
  → no coverage claim). The UI's `fmtPct` renders `null` as a dash.
- `/signoffs` items carry `approver` (the verifier's principal id) and `evidence` (the
  snapshot stamped at write time).
- `/oracle/{repo}` uses `strength` / `strength_mean` / `mutants` / `killed` / `gate`.
- `ladder` in `POST /runs` is a list of rung labels (`r1`, `r2` …), as the core's run
  orchestrator defines it; `builder:model[:provider]` triples are accepted as labels too.
  The worker resolves a bare label to the run's own `builder:model[@provider]` (W3-B; before
  that every API-created replay failed at the worker with `rung 'r1' must look like
  builder:model`); the stored `ladder` stays what was declared; `trial` on ledger rows is
  positional (`r1`, `r2` …) either way.
- `GET /runs/{id}` carries `builder_config` (`{}` when none) — W3-B. The UI's run dialog
  offers it as a validated JSON editor plus a one-click "Use my Claude Code login (dev)"
  toggle (`{"auth": "cli"}`).
- `POST /runs` accepts `retain: {worktrees, transcripts}` (both default `false`) — per-run raw retention chosen by the operator at queue time, stored under `params.retain`, served on the run, honoured by the worker (worktrees under its scratch, transcripts under `<home>/transcripts/<run>`). ADR-0006's zero-retention default is unchanged.
- The retained artefacts are REACHABLE from the evidence drill-down (C13): `GET /grades/{row_hash}/patch` / `/transcript` / `/retained` and the `/reviews` family. The UI's readings live in `ui/src/screens/Runs/contract.ts` (types, hooks, a dependency-free SHA-256 and the diff parser) until they are folded into `api/types.ts` / `api/hooks.ts`. The evidence drawer's Patch tab fetches the patch as bytes, hashes them in the browser and compares with the pack's `diff_sha256`; the Review panel sends that hash as `patch_sha256` and stays disabled until the Patch tab was loaded in the session and the hashes agree. The API host must see the worker's `CRB_HOME` (the walkthrough and the compose stack share it); on a split deployment the patch route answers 404 `patch_unavailable` with the reason.
- **The budget is a measured variable, not a fixed cap (C8).** `POST /runs` accepts a run-level
  `budget` and object rungs `{builder, model, provider?, budget?}` in `ladder` (above). The
  worker stamps every ledger row it writes with two hashed labels: `labels.budget_tier` =
  `<max_tool_calls>/<max_turns>/<wall_clock_s>` of the budget the attempt actually ran under
  (`25/25/900` is the builder default; when a token or dollar cap is also engaged the tier
  appends `/tok=<n>` and/or `/usd=<x>`, because attempts that differ only there were not the
  same experiment), and `labels.rung_index` = the 0-based index of the rung in the run's
  ladder (`trial` stays positional, `r1`, `r2` …). The tier is computed by the same
  `budget_for_rung` call the build adapter makes, so the label and the cap cannot disagree;
  the evidence pack's `builder.budget` carries the full budget. The budget is NOT part of the
  cell key — a sweep lands in one cell and is split by `labels.budget_tier` after the fact
  (`/grades` rows carry `labels`; `/runs/{id}/tasks` carries `budget_tier` / `budget_tiers`).
  **Contract: a blind rate quoted without its budget tier is not a claim** — the NHS
  measurement (docs/reviews/2026-09-14-nhs-public-repos.md §3) found 6 of 8 blind misses
  were `budget` at the fixed `25/25/900`; the rate at that tier is a fact about the cap, and
  only a rate stated *at a tier* (or a sweep across tiers) says anything about the model.
- `/repos` items carry `clone_path` (empty for a URL-only registration until the worker's
  first run clones it — W3-B).
- `GET /settings` (admin, W2-A) still returns `Settings.redacted_dict()`; the UI's
  `{builders, sandbox_mode, retention, oidc_enabled, ledger_backend, apparatus_version,
  policy_version}` reading is NOT yet served — see the W2-B report.
- `GET /capability-map`, `GET /routes` and the new `GET /failure-split` (A2, review action #4)
  carry the `failure_kind` split, `model_point` and the repo's `controls` verdict; the UI's
  readings live in `ui/src/screens/Capability/contract.ts` (extended types + hooks) until they
  are folded into `api/types.ts` / `api/hooks.ts`. `GradeRow.to_dict()` now also carries
  `failure_kind` and `cost_known` (derived — not part of the hashed body; new rows pin them
  into the hashed `labels`); `/grades` still serves the stored columns only, so read the split
  from `/failure-split`. Run detail reads `/failure-split?repo=&run_id=` for its split tiles.
