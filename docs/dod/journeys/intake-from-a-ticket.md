# Take work from a ticket (ADO / Jira column → gap feedback → backlog)

**Purpose.** A person moves a ticket into one column on their own board (Azure DevOps first,
Jira second) and the product treats that as the request to manufacture: it reads the ticket,
tells the ticket what is missing before any spend, registers it as the backlog item when the
gaps close, delivers the pull request, and moves the ticket when the pull request is merged.
Nothing is typed twice: the ticket is the backlog item, the column is the consent gate
(scratchpad `INTAKE-DESIGN.md`; not yet in the product's own words — see G-007).

**Entry → exit.** Entry: a ticket enters the watched column on the enterprise's board, on a
repository whose listener an operator switched on. Exit: the ticket carries the product's
comment (what is missing, or the pull request link), its label (`crb:needs-info` ·
`crb:ready` · `crb:not-deliverable` · `crb:queued`), and after the merge its state moves per
the configured mapping; inside the product the same item shows on the Factory list with its
chain. Today the only entry is the Factory screen's freeze form or `POST /factory/{repo}/backlog`
(`docs/ONBOARDING-A-REPO.md` Step 8); no ticket path exists.

**Non-goals.** The product never edits ticket fields other than its own label, its comments
and the one state transition the mapping allows. It never creates tickets. It never reads a
column it was not pointed at. It does not replace the freeze form or the evolutions route —
the ticket path lands on the same `POST /factory/{repo}/backlog` and
`POST /factory/{repo}/backlog/evolutions`. Discovery and inception capture (Jira/Slack/meeting
notes) stay out of scope (DL-001). GitLab / Azure DevOps as the *repository* host (F21) is a
separate item: this journey delivers the pull request to GitHub through the App (ADR-0014).

## Gaps
- **G-001** — No tracker connection exists: add an `intake` settings block (`tracker: ado|jira`, organisation/site URL, project, watched column or state, area path or JQL, `intake_poll_s`, `enabled` default OFF per repository) to `src/crb/server/settings.py` and a tracker secret in the product's own secret store, stored and read back as a fingerprint like the GitHub App key · owner server.
- **G-002** — No poll: `Worker.run_forever`'s idle loop reads each switched-on repository's column every `intake_poll_s` through the `TrackerClient`, keeps an idempotency key (tracker, key, revision) on the chain, queues registrations that arrive while a factory run is active (today `409 factory_run_active`), and records every stop (unreachable, secret missing, write refused, column gone) as an `intake.*` event with a reason the health probe and the screen serve · owner server.
- **G-003** — No pull mapping: `src/crb/intake/{ado,jira}.py` behind one `TrackerClient` protocol (`entered(column, since)`, `read(key)`, `comment(key, text, marker)`, `label(key, value)`, `transition(key, state)`, `link(key, url)`) map fields to a draft `BacklogItem` — id `<tracker>-<key>`, HTML/ADF → text, acceptance criteria → `acceptance_criteria` and `slot: text` structural facts, tags → labels, story points → size tier, work-item type → class hint — with a classifier over title + description that serves its confidence, a stated default rule for `level` and `kind`, and a re-read at a new revision registered as an evolution with `supersedes` · owner factory.
- **G-004** — No gap feedback leaves the product: a readiness-comment renderer turns `open_questions()` plus the pre-run `cell_route` (route, n, Wilson interval, false-Q1, apparatus) into one idempotent comment (marker) on the ticket, sets `crb:needs-info` / `crb:ready` / `crb:not-deliverable`, records `intake.feedback.posted` on the chain and serves the same text on the intake row · owner factory.
- **G-005** — No freeze from the ticket: when the draft's structural gaps are closed the poll registers it through `POST /factory/{repo}/backlog` (or `/backlog/evolutions` when it supersedes), sets `crb:queued` with the item link, and posts the pull request link or the refusal with its served `way_forward` back on the ticket, each recorded on the chain · owner factory.
- **G-006** — No outcome mapping: an `intake.outcome_map` setting (`merged → <state>`, `closed → <column> + comment`) applied by `sync_outcomes` through `TrackerClient.transition`, recorded as `intake.transitioned` on the item's chain, default no transition · owner server.
- **G-007** — No intake screen: a `/factory/intake?repo=` route (`GET /factory/{repo}/intake`) listing the column's tickets with draft, readiness state, label, feedback text, item link and the listener state; `Switch the listener on/off`, `Re-read the column now`, `Post the feedback again` with success and error states; an About block, a journey eyebrow, a `SCREENS` entry in the ratchet and a `HELP[]` entry with a guide anchor · owner ui.
