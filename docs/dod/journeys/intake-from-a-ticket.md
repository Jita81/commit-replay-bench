# Take work from a ticket (ADO / Jira column → gap feedback → backlog)

**Purpose.** A person moves a ticket into one column on their own board (Azure DevOps first,
Jira second) and the product treats that as the request to manufacture: it reads the ticket,
tells the ticket what is missing before any spend, registers it as the backlog item when the
gaps close, delivers the pull request, and moves the ticket when the pull request is merged.
Nothing is typed twice: the ticket is the backlog item, the column is the consent gate. The
product says so in its own words on `/factory/intake` (the About block and the journey
eyebrow), in ONBOARDING-A-REPO step 9, in OPERATOR §11 and in ADR-0017.

**Entry → exit.** Entry: a ticket enters the watched column on the enterprise's board, on a
repository whose listener an operator switched on. Exit: the ticket carries the product's
comment (what is missing, or the pull request link), its label (`crb:needs-info` ·
`crb:ready` · `crb:not-deliverable` · `crb:queued`), and after the merge its state moves per
the configured mapping; inside the product the same item shows on the Factory list with its
chain.

**Non-goals.** The product never edits ticket fields other than its own label, its comments
and the one state transition the mapping allows. It never creates tickets. It never reads a
column it was not pointed at. It does not replace the freeze form or the evolutions route —
the ticket path lands on the same `POST /factory/{repo}/backlog` and
`POST /factory/{repo}/backlog/evolutions`. Discovery and inception capture (Jira/Slack/meeting
notes) stay out of scope (DL-001). GitLab / Azure DevOps as the *repository* host (F21) is a
separate item: this journey delivers the pull request to GitHub through the App (ADR-0014).
