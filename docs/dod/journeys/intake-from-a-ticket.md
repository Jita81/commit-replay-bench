# Take work from a ticket (ADO / Jira column → gap feedback → backlog)

**Purpose.** A person moves a ticket into one column on their own board (Azure DevOps first,
Jira second) and the product treats that as the request to manufacture: it reads the ticket,
tells the ticket what is missing before any spend, registers it as the backlog item when the
gaps close, delivers the pull request, and moves the ticket when the pull request is merged.
Nothing is typed twice: the ticket is the backlog item, the column is the consent gate. No
screen or guide says this in the product's own words yet — see G-335.

**Entry → exit.** Entry: a ticket enters the watched column on the enterprise's board, on a
repository whose listener an operator switched on. Exit: the ticket carries the product's
comment (what is missing, or the pull request link), its label (`crb:needs-info` ·
`crb:ready` · `crb:not-deliverable` · `crb:queued`), and after the merge its state moves per
the configured mapping; inside the product the same item shows on the Factory list with its
chain.

**Non-goals.** The product never edits ticket fields other than its own label, its comments
and the one state transition the mapping allows. It never creates tickets. It never reads a
column it was not pointed at. It does not replace the freeze form or the evolutions route —
the ticket path lands on the same `POST /factory/{repo}/backlog` and
`POST /factory/{repo}/backlog/evolutions`. Discovery and inception capture (Jira/Slack/meeting
notes) stay out of scope (DL-001). GitLab / Azure DevOps as the *repository* host (F21) is a
separate item: this journey delivers the pull request to GitHub through the App (ADR-0014).

## Gaps
- **G-900** — no tracker connection exists, so no column can be watched · add an `intake` settings block (`tracker: ado|jira`, organisation or site URL, project, watched column or state, area path or JQL, `intake_poll_s`, `enabled` default OFF per repository) to `src/crb/server/settings.py` and a tracker secret in the product's own store, read back as a fingerprint like the GitHub App key · server
- **G-901** — nothing polls the watched column, so a ticket never reaches the product · read each switched-on repository's column every `intake_poll_s` in `Worker.run_forever`'s idle loop through the `TrackerClient`, keyed by (tracker, key, revision) on the chain, queueing a registration refused with `409 factory_run_active` and recording every stop as an `intake.*` event the health probe and the screen serve · server
- **G-332** — no mapping turns a ticket into a draft item · add `src/crb/intake/{ado,jira}.py` behind one `TrackerClient` protocol (`entered`, `read`, `comment`, `label`, `transition`, `link`) mapping fields to a draft `BacklogItem` (id `<tracker>-<key>`, HTML or ADF to text, acceptance criteria to structural facts, story points to a size tier, a classifier class with its confidence) and registering a re-read at a new revision as an evolution with `supersedes` · factory
- **G-902** — no gap feedback leaves the product, so the ticket never learns what is missing · render `open_questions()` plus the pre-run `cell_route` (route, n, Wilson interval, false-Q1, apparatus) into one idempotent marked comment on the ticket, set `crb:needs-info` / `crb:ready` / `crb:not-deliverable`, record `intake.feedback.posted` and serve the same text on the intake row · factory
- **G-333** — nothing freezes a ticket into the backlog · register the draft through `POST /factory/{repo}/backlog` (or `/backlog/evolutions` when it supersedes) once its structural gaps close, set `crb:queued` with the item link, and post the pull request link or the served `way_forward` back on the ticket, each recorded on the chain · factory
- **G-334** — the recorded merge outcome never reaches the ticket · add an `intake.outcome_map` setting (`merged → <state>`, `closed → <column> + comment`) applied by `sync_outcomes` through `TrackerClient.transition` and recorded as `intake.transitioned` on the item's chain, default no transition · server
