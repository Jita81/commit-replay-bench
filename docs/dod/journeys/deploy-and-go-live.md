# Deploy and go live

**Purpose.** The operator deploys the stack once (ONBOARDING-A-REPO Step 0) and leaves with a running API and worker whose health is green, the builder credential and the GitHub App registered, an approver account created, the bootstrap admin rotated or replaced by OpenID Connect, and a printable posture statement for the review board — the DEPLOYMENT §8 go-live checklist, proven by the product where the product can read it.

**Entry → exit.** Entry is out of band: Compose or Helm, PostgreSQL, `CRB_OIDC__*` or the bootstrap admin, `CRB_BUILDER__EXECUTOR=docker`, `deploy/verify-image.sh`, `crb doctor`, backups (DEPLOYMENT §1–§4, §8). The first in-product screen is `/login`. The admin then reads the health card and stores the builder token, syncs the GitHub App installations and creates the approver on `/settings`; reads the five posture lists on `/posture`, where every row that is not the production posture names its next step; and lands on `/home`, where the task list reads "n of 8" and task 7 "Invite an approver" is Completed. Nothing spends money on this journey.

**Non-goals.** Connecting a repository (dod.journey.connect-a-repository), recovering an account (dod.journey.recover-an-account) and measurement are other journeys. The host acts on the checklist that the product cannot read — image digest match, egress test from a worker pod, PITR and a rehearsed restore, the out-of-band `row_hash` record, dashboard alerts, a live OIDC rehearsal, a penetration test — remain the operator's; the product's job is to prove what it can read and to say plainly which lines it cannot.

- **G-951** — uv, poetry and pylock locks are refused in the sealed posture (`PROVISION_LOCK_UNSUPPORTED`) · read each lock format into the same pinned, hashed set a requirements lock gives · server
