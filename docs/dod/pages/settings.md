# Settings

**Purpose.** The instrument's health, the builder sign-in, the GitHub App, the reader's own password and, for admins, the non-secret configuration and user accounts. Secrets are never returned by the API and never shown here (help.ts `/settings`).

**Entry → exit.** An admin arrives from the nav "Settings" link (shown to admins only; the route itself is open to every signed-in role), from Home task 7 "Invite an approver", or from a "Settings" link on a Posture row that is not the production posture. They read the health card (every probe with its detail line, and the crb · apparatus · policy version line), store or verify the Claude Code token, read the GitHub App state and sync its installations, read the redacted configuration (sandbox mode, ledger backend, apparatus, policy, OIDC, builders, retention), and, in the Users card, read every account with its kind (local or identity provider), role, active state and last sign-in, change a role, turn an account off and on, set a new password, sign it out on every device, read that account's own history of changes and sign-ins, and create a local account — after which the card offers the next step (back to Home, or on to Connection). Under Go-live attestations an admin records each act of the go-live checklist that only the operator can do — the day and what was done — and withdraws one that no longer holds; the Deployment page then shows it attested. Every signed-in role also changes its own password in the "Change my password" card. A non-admin sees health, their own password card, the token's presence and the GitHub App card, then a Configuration card that reads "Admin only" with the reason. The page offers guide links (Register the GitHub App, How credentials are held, When the sandbox is unavailable, How sign-in and roles work, the go-live checklist and how to record what only the operator can prove) and no in-app next step.
**Entry → exit.** An admin arrives from the nav "Settings" link (shown to admins only; the route itself is open to every signed-in role), from Home task 7 "Invite an approver", or from a "Settings" link on a Posture row that is not the production posture. They read the health card (every probe with its detail line, and the crb · apparatus · policy version line), store or verify the Claude Code token, read the GitHub App state and sync its installations, read the redacted configuration (sandbox mode, ledger backend, apparatus, policy, OIDC, builders, retention), and, in the Users card, read every account with its kind (local or identity provider), role, active state and last sign-in, change a role, turn an account off and on, set a new password, sign it out on every device, read that account's own history of changes and sign-ins, and create a local account — after which the card offers the next step (back to Home, or on to Connection) — and invite the second person in the Invite an approver card: the deployment's two-person readiness in the server's own words, an inactive account plus a one-time link shown once, and every invitation with the state it is in. Every signed-in role also changes its own password in the "Change my password" card. A non-admin sees health, their own password card, the token's presence and the GitHub App card, then a Configuration card that reads "Admin only" with the reason. The page offers guide links (Register the GitHub App, How credentials are held, When the sandbox is unavailable, How sign-in and roles work) and no in-app next step.

**Non-goals.** The page does not register the GitHub App (that is `CRB_GITHUB__*` on the host; the card says so and links the guide) and does not configure OpenID Connect (`CRB_OIDC__*`; shown read-only as enabled or disabled). It does not show a secret value: a builder is configured or not, a stored token is at most its last four characters, and a password is sent once and never shown back. It offers no email reset, no self-service unlock and no security questions — when nobody can sign in at all the way back is `crb users` on the API host. It does not run measurement.
