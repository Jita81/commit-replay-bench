## Part A — the reviewer's assessment (condensed, their numbering)


## Executive assessment
"This is substantially more important than a conventional benchmark." CRB turns AI delivery capability into a locally measured, governed control system: Repository → historical evidence → task classes → controlled build → mechanical verification → evidence → routing policy → governed production. "An empirical control plane for deciding what an AI software builder may be trusted to do in a particular software environment." Tension: much stronger as a measurement instrument than as evidence for autonomous software delivery; safeguards can create false certainty if the boundary between what the benchmark proves and what the organisation wants to trust is not kept sharp.

## Points (numbered as the reviewer numbered them)
1. Gets right: measures P(success | model, repository, task class, size, mode, context, process, environment, verifier), not P(success | model).
2. Repository-local thesis strong; the NHS 15/18 sighted vs 2/14 blind shows the task representation determines accessible capability (fits Context Engineering).
3. The five belts are a very good design (tests unchanged / target green / no new failures / source changed / repo lint).
4. False-Q1 at write is arguably the most important engineering decision; "no evidence pack → no pass" excellent.
5. Negative controls impressive — they found an actual instrument defect (the poison-target bug).
6. Limitation: controls give known-cheat detection assurance, not general adversarial robustness. Next step: GENERATIVE adversarial controls, measure P(escape | adversarial control).
7. Oracle problem correctly identified; mutation score measures oracle strength, not specification completeness nor production safety — make the three-way boundary explicit.
8. CRB + Automated Agile: the closed-loop software manufacturing stack; the benchmark is the factory's feedback mechanism.
9. Routing rule useful and dangerous: thresholds (0.90, Wilson-low 0.80, n=10) are POLICY choices; separate measurement layer from policy layer even more explicitly; n=10 is small for high-consequence decisions.
10. Size taxonomy (LOC) underpowered: distinguish change volume from change complexity (files, fan-out, API surface, control flow, boundaries crossed, data model, integrations, test delta, semantic risk, reversibility).
11. Change-class taxonomy is a valuable asset: the capability map as a routing matrix is the commercial proposition ("here is the empirically demonstrated boundary at which your AI factory can operate").
12. Sighted/blind distinction excellent; could become a context-engineering laboratory with multiple context conditions.
13. Strongest future experiment: context ablation (repo only / +message / +tests / +architecture map / +ADRs / +context package / +process / +feedback), measure ΔP(success) per layer.
14. "Process is the lever" (8/12 vs 0/12) potentially huge but n=12; wants a factorial Model × Process × Context × Verification experiment; capability threshold below which process cannot compensate.
15. Blind NHS 2/14 needs careful interpretation: state it locally ("under this repository, sample, builder, apparatus, rung-0 budget"), do not extrapolate.
16. Host-executor limitation is a serious open issue: sealed posture designed, not demonstrated at campaign scale.
17. Historical commit replay has selection bias: measures P(AI solves testable historical changes), under-represents architecture, ambiguity, migrations, ops, security design, UX, undocumented rules — establish the domain of validity explicitly.
18. The commit is not the true specification (Slack, tickets, tacit knowledge missing) — CRB measures reproduction of the observable result from available information, not the original reasoning.
19. Dependency eras excellent; wants evidence on OS image, compilers, libc, runtime, registry contents, services, clocks, locale, randomness, network tests, DB/browser versions.
20. Hash chaining = integrity evidence, not truth evidence; trust hierarchy self-report → structured event → captured output → independent reproduction → cryptographically bound; don't let "hash-chained" mean "verified".
21. Sign-off conceptually excellent; the artefact must record reviewer identity, exact diff, task, tests observed, evidence, concerns, decision, timestamp, apparatus; force the reviewer to say what they examined.
22. "Third-party review, never grade" principle excellent — carry into Automated Agile.
23. Factory mode is the really interesting bit: a governed AI SDLC with an explicit human merge boundary.
24. RED proof circularity: a model-backed test author would move the oracle problem upstream (AI test validating AI code) — needs an independent verification layer.
25. Most important missing metric: rework — first-pass rate, eventual acceptance rate, mean attempts to acceptance, human minutes per accepted change, AI cost per accepted change, elapsed time, total cost of accepted change.
26. "20 % human finishing" needs measurement: intervention categories 0–5 or actual human edit distance/time.
27. Binary clean/not-clean where reality is continuous: keep the gate, add an intervention-burden axis.
28. Cost figures need normalisation: cost per ACCEPTED change (AI + human finishing + infrastructure) / accepted changes.
29. Any "2000 user stories/hour" claim (from Automated Agile material) must not be headlined from this benchmark; the metric is verified changes per hour and human hours per verified change.
30. Repository architecture unusually disciplined (stdlib core, import-linter, ADRs, decision log, navigation headers, code map, hermetic tests, append-only, evidence packs, apparatus versions) — the headers are agent-friendly.
31. 3,400 tests are not automatically evidence of quality; don't market the number.
32. Biggest methodological concern: independence — the repo's own tests encode the original implementation's assumptions; a model reproducing those assumptions scores without solving the requirement. Proposes historical oracle + independent oracle + production oracle.
33. "Oracle triangulation": OracleConfidence = f(mutation, independent tests, behavioural coverage, production invariants).
34. "Trust" is overloaded: execution / verification / security / operational / organisational / business trust. `deliver` must mean "satisfies this repository's defined automated acceptance policy", never "safe to deploy autonomously".
35. Genuinely novel: the autonomy boundary discovered per repository rather than declared globally — an AI capability map per repository.
36. The capability map as the factory's control plane: evidence-driven rather than model-driven.
37. Reframe from "benchmark" to "compiler": repository + evidence + builder + class + size + mode → AUTONOMY POLICY (a YAML per repo/apparatus/builder/mode).
38. What to build next, in order: measure human finishing; context ablation; independent oracle; larger cells (30/50/100+ distinct tasks); sealed campaign; difficulty model (size/complexity/risk/coupling); economic model (£/accepted change, human minutes/accepted change, accepted changes/engineer-day); longitudinal decay — Trust(t), re-measure monthly.
39. Change the model, don't change the benchmark: same model across context/process conditions to quantify the delivery system's contribution.
40. Overall table: core idea very strong; practical usefulness very high; measurement discipline strong; repository-local excellent; negative controls excellent; evidence/ledger strong; oracle treatment strong but incomplete; statistical maturity good foundation/early evidence; security evidence not yet demonstrated; production autonomy evidence not yet demonstrated; sample sizes small; historical-task bias material; context-engineering and software-factory relevance extremely high; commercial potential potentially significant. Weaknesses mostly acknowledged by the project itself.

Conclusion: the important output is "for this repository, under this context condition, using this builder and process, the evidence supports this particular boundary of autonomy" — a new kind of engineering artefact; make measurement and routing part of the factory itself. Caveat: not a source-code audit.

## 1. Summary

The reviewer read the product correctly from the outside: the thesis (capability is measured per repository, per class, per size, per builder, under a named apparatus — never as P(success | model)), the five belts, false-Q1 refused at write, the negative controls, the evidence packs, the sighted/blind split and the routing rule are all as described, and each is enforced where the reviewer hoped it would be (`GradeResult.__post_init__`, `GradeRow.assert_invariants`, database triggers, a CI gate over 1,071 census rows, the `ControlsVerdict` clauses in `route()`). Where the source contradicts or already answers them: the "2000 stories/hour" claim appears nowhere in this repository `[measured: grep]`; no document equates the hash chain with truth (`docs/REPRODUCING-THE-CENSUS.md` §0 separates "the ledger's internal consistency" from "the belts' truth"); the test count is never used as a quality claim; the sign-off record already stamps identity, evidence, policy thresholds, controls, apparatus and a mandatory attestation; the per-change human verdict (`crb.core.review.ReviewRecord`) is anchored to the bytes read; `deliver` is already defined as "high-confidence candidate under the published bar, not safe for autonomous delivery" (EVIDENCE-AND-CLAIMS §6) — though not yet in the README's "What it is not"; and the domain-of-validity caveats the reviewer asks for exist, scattered across four documents rather than stated once. Three findings from the source change the backlog: **(1) the capability map does not yet gate the factory** — `FactoryLoop._deliver` opens a PR for any clean build when `deliver=True` is set on the run and only *prints* the route decision in the PR body (`src/crb/factory/loop.py:406`, `src/crb/factory/delivery.py:277`), so the reviewer's "map as control plane" is `[aspiration]` in code; **(2) the measurement/policy separation is asymmetric** — a sign-off stamps `policy_thresholds` and `relaxed` into every record, but a `RouteDecision` carries only the version string, and `crb route --policy-json` accepts loosened thresholds under the unchanged `routing.v1` label (`src/crb/cli/commands/route.py:79`; the server cannot do this — it uses `DEFAULT_POLICY` only); **(3) human finishing and the economics of an accepted change are recorded only in pieces** — per-attempt cost/latency/rung and `first_pass_clean` vs `clean` exist, `ReviewRecord.mergeable` plus typed findings is a five-level intervention category, but no field holds human minutes, the PR's merge outcome or cost-to-accept, and the only measured reading is ten NHS patches, four mergeable as-is `[measured, n = 10]`.

## 5. What the reviewer could not see and now can

A source audit finds that the write-time invariant is not one check but a stack — a frozen dataclass that cannot be instantiated in a false state (`GradeResult.__post_init__`, `GradeRow.assert_invariants`), database triggers that refuse `UPDATE` and `DELETE` on five tables and are re-asserted on every `/health` call, the same predicate re-run in SQL over the stored belts before any sign-off, and a CI test that pins the 1,071 census verdicts to exact counts and says in its docstring not to "fix the test". It finds that the negative controls keep honest books about their own limits: a cheat that cannot be built for a task is `not_constructible` with the toolchain's reason and counts against the constructible share the router demands (≥ 0.5), a control that compiles but goes red for the wrong reason is refused as evidence, and an escape is stamped on the task and withholds `deliver` for the whole repository rather than being averaged away. And it finds that nothing raw leaves an execution sandbox unredacted — every test tail, lint tail, service log, error string, review statement and sign-off note passes `crb.core.redact` before it is stored, the caps cut after redaction so a secret cannot straddle the cut, diffs are held only as hash plus counts and served on demand from a retained worktree against that hash — while also finding the three things this document names that the material could not show: a route that is printed on the PR rather than enforced on it, a routing policy whose thresholds are not yet stamped where the sign-off's are, and a human-finishing cost that is measured once, by hand, on ten patches.
