## 2. What "its body" means

It means the request body the run was filed with: the JSON sent to `POST /runs`. This is
unchanged from version 1, and the checker found the quotes exact.

- R5 item 2: "the script reads run records and run bodies only, and no row". Records and
  bodies are two things.
- Part E item 5: "from run bodies and from each run record's status, row count, filing time
  and end time".
- Test (e): "It is `A0` when the body carries no `arm` field, or `arm: "A0"`, and no
  `test_author`." The served code accepts only `"S1"` for `arm` and forbids extra fields, so
  no stored record could hold `arm: "A0"`. The words describe what was sent.
- Where the text means the served copy it says so: test (c) reads times "from the run record
  as the product serves it". Test (e) has no such words.

**The text settles the meaning.** It does not say who holds the body.

Correction to version 1 (checker's note 1). The plan file is not "the only existing copy".
The product keeps a derived copy in `params_json`: stripped, and holding only the keys that
were set. No GET serves it. So the plan file is the only copy a script can read.

## 3. The source, and the tie of a body to a run

### 3.1 The facts that broke version 1's condition 1

Version 1 said a body counts only if one file holds the run id next to the body, and that a
tie made by inference fails. Neither can be met:

- The body and the run id are in two files joined by a key such as `click-1/1`. The plan
  file `wave-batches.json` holds the body under the key. The out files `click-out.json` and
  `cobra-out.json` hold the run id under the same key.
- When a POST timed out, the poster took the newest run it did not already hold whose sorted
  `task_ids` equal the body's. That tie is by inference. The out file does not say whether
  a run was taken this way. The terminal text is not kept. The delivery manager does not
  recall a timeout but cannot prove there was none.

So for every one of the 49 runs, the script cannot show that the tie was made from the POST
response. I do not pretend it can.

### 3.2 What the script may accept as "its body" (the harder reading)

**A run's body is the `body` value the plan file holds under the key under which an out file
holds that run's full id.** For run `98fe708c` the out key is `click-3/1#attempt1` and the
plan key is `click-3/1`. No other suffix key is accepted.

The script does not make or mend a tie by `task_ids`, by times or by file order. It takes
the poster's key as given and then tests it. Every test below can only fail the check.

- **T1. Files fixed by hash.** The script carries the sha256 of each file it opens, as the
  second fact sheet gives them: the plan file `ae705b68...fb45a`, its copy from before the
  `S3` batches were added `a3c592cd...2970fd`, `click-out.json` `27b2747e...4c4170`,
  `cobra-out.json` `59d7eefc...06e0e1`. It refuses a file whose hash differs. It prints the
  four paths and hashes.
- **T2. The two plan copies agree.** For each of the 48 wave keys, the `body` in the plan
  file and the `body` in the copy from before `S3` must be equal as parsed JSON. The copy is
  the nearer of the two to the time of filing.
- **T3. Keys.** The out files together must hold exactly 49 keys: the 48 keys
  `<repo>-<batch 1 to 6>/<place 1 to 4>` for click and cobra, and `click-3/1#attempt1`. Any
  other key, a missing key, or a key in the wrong repository's file fails.
- **T4. Ids.** The 49 `run` values must be 49 different full run ids. The 48 under the
  plain keys must be exactly the 48 standing ids the script carries. The one under
  `click-3/1#attempt1` must be the run that test (a) matches to `98fe708c`.
- **T5. The key agrees with the product.** For each plain key, the run under it must, by
  its run record, hold the `task_ids` of that repository's batch of that number in
  Amendment 2, and its place by test (d) must equal the place in the key. For
  `click-3/1#attempt1`, the run must hold the `task_ids` of click batch 3 and meet the
  times test (g) gives run `98fe708c`.
- **T6. The body is not contradicted by the run record** (section 4).
- **T7. How the place in the key is formed.** Before the script is committed the delivery
  manager records, from the poster's source text with its sha256 and line, whether the place
  number in a key is the entry's position in the batch's `runs` list or its `slot` value.
  The script follows that record. This is a name check of the same kind as test (h).

If any of T1 to T7 fails for any run, test (e) fails and test (i) applies.

### 3.3 The possible inferred tie

What can be checked. If tests (a), (b), (d), (f), T3, T4 and T5 all pass, then each batch has
exactly four standing blind runs on its commits, each sits under one key of that batch, and
each key's place equals the run's rank by the product's own filing time. Under those facts a
tie made by inference cannot have picked a wrong blind run and still pass:

- A run that is not blind, or not on the batch's commits, fails (a) or T5.
- A second run made by a POST that timed out and was then posted again would be a fifth
  blind run on the batch's commits. That fails (b).
- A run of the same batch under the wrong key fails T5, because its filing-time rank would
  not match the key's place.

So the script does not need to know which ties were inferred. T5 tests every tie the same
way, against times the product serves.

What cannot be checked, and is taken on trust:

1. That the poster sent the plan's `body` for place `p` as its `p`th POST of the batch, and
   sent it unchanged. This rests on the poster's source text (`wave4_post.py` line 150,
   sha256 `b30ca68e...50b105`) and on the delivery manager's statement that the plan file
   was not rewritten by the poster.
2. That the four files are as they were at filing time. The hashes were first recorded on
   2026-11-12, after the wave. The script cannot use file times.
3. Whether any tie was made by inference. No kept file says.
4. That `refile.py` filed batch 3 again from the same plan entries.
5. That the poster source text of item 1, at that sha256, is the text that ran for every
   batch. The deviation log (annex, D4) records a poster crash before batch 3. No kept file
   shows which text ran after it. T7 rests on the same text.

**The script prints these five lines in its output, word for word, under the heading "Taken
on trust".** The report repeats them on the page that states the primary. If the amendment
is in force the report adds one sentence and no more: "For all 49 runs the product's `s1`
flag agreed with the `arm` field of the body." The flag is `body.arm is not None` (`runs.py`
1246). It shows that an `arm` field was sent. It does not show `test_author`, and it does
not show that the rest of the body was sent unchanged. So trust item 1 still stands, less

I record the plain consequence. With T5 in place, the out files add corroboration, not
proof. The weight of test (e) on the arm rests on trust item 1. With P2 in force, the `arm`

## 4. "Not contradicted by the run record", field by field (checker's fault 1)

Version 1 said "equal" and no more. Read literally that fails all 49 runs on `retain`, which
is not a mismatch. The rule is now fixed. The script writer decides nothing.

General rules:

- Only keys the body carries are compared. A key that is absent, or whose value is null, is
  not carried.
- JSON numbers are compared as numbers: `6` equals `6.0`. A boolean is not a number and a
  string is not a number.
- Strings are compared exactly. Nothing is stripped, folded or repaired.

| Body key | Served field of the run record | Rule |
|---|---|---|
| `repo` | `repo` | equal strings |
| `kind` | `kind` | equal strings, and the value is `blind` |
| `task_ids` | `task_ids` | same length, same strings, same order |
| `builder` | `builder` | equal strings |
| `model` | `model` | equal strings |
| `provider` | `provider` | equal strings |
| `max_cost_usd` | `max_cost_usd` | both are numbers and equal as numbers. A served null fails |
| `budget` | `budget` | take the body's `budget` without its null-valued keys. The served object must have exactly the same keys, each value equal (numbers as numbers) |
| `builder_config` | `builder_config` | exactly the same keys, each value equal as a JSON value |
| `retain` | `retain` | a subset test. Each key the body carries must equal the served key. Each served key the body does not carry must be `false` |
| `campaign_id` | not served | not compared here. It must equal the campaign id (section 8) |
| `env_stop`, `outage_stop`, `learning` | not served | not compared. The report says so |
| `arm`, `test_author` | not served | not compared. They are the subject of test (e) |

- **`ladder`.** The registered body sends no `ladder`, and the delivery manager's list of
  body keys has none. The served `ladder` is the stored default, not something sent. It is
  not compared and the script drops it. A body that carries `ladder` falls under the next
  rule.
- **Any other key.** A body that carries a key outside this table stops the check. The
  script prints the key name and the run id. This is a failure under test (i). It is not
  mended in the script.

I checked at `7bb03d6c` that the served code does not rewrite these on the way in or out:
`task_ids` (`schemas.py` 914-921, `runs.py` 574), `builder_config` (`schemas.py` 835-864,
`runs.py` 575), `budget` (`schemas.py` 511-513, `runs.py` 567), `max_cost_usd` (`runs.py`
568, a float), `retain` (`runs.py` 750-751 and 576, `schemas.py` 647-653). I did not trace
`builder`, `model` and `provider` beyond `new_run` (`runs.py` 732-737). Before the script is
committed the delivery manager confirms from the served code that none of the ten rows above
fails a body for a rewrite the code itself makes. If one does, this ruling is revised first.
The script writer does not choose.

A mismatch on any row means the file is not that run's body. Test (e) fails and test (i)
applies.

## 5. What the script may read from the poster's files (checker's note 3)

**Plan file and its copy.** For each of the 48 wave keys, the `body` value. If section 3.2
T7 records that the place comes from `slot`, also `slot`. Nothing else. The script drops
`arm`, `cell`, `coin` and `order` as it parses. It does not open the `S3` batches. The
poster's `arm` label is not the body: reading it would break "from its body only". The
expected arm of each place comes from Amendment 2's orders, which the script carries.

**Out files.** For each of the 49 keys, the `run` value. Nothing else. The script drops
`arm`, `posted`, `ended` and `clean_end` as it parses, and never stores, logs or prints one.

- `arm` is the poster's label. It is not the body.
- `posted` and `ended` are times. Test (c): "Nothing else is used as a time".
- `clean_end` is a status flag. Test (a) reads status "from the run record's own fields".

This is in force only under P1.

**Nothing else from that folder.** No response, poll, log or login file. No seat opens the
folder to learn an arm. The delivery manager's second fact sheet read key names and the
`test_author` values. That is recorded in section 6.

**Read as it is.** The script parses the kept JSON and applies test (e) to the `body` as
written. A field that is absent or null counts as absent. `test_author` is compared with `L`
by exact equality, with no strip and no case fold.
